## 2. หลักร่วมที่ตกผลึกได้

### 2.1 เริ่มจากสิ่งที่กรรมการต้องตัดสิน ไม่ใช่เริ่มจาก Feature

Proposal ต้องช่วยให้กรรมการตอบได้ภายในเวลาไม่นานว่า:

1. ปัญหานี้จริงและสำคัญหรือไม่
2. ใครเจอปัญหา และเกิดในจังหวะใด
3. ของเดิมยังขาดอะไร
4. แนวคิดนี้ทำงานอย่างไร
5. ทำไมจึงดีกว่าหรือแตกต่าง
6. ทำได้จริงแค่ไหน และมีข้อจำกัดอะไร
7. หากทดลอง จะวัดความสำเร็จอย่างไร

### 2.2 ใช้ Problem–Gap–Mechanism–Impact เป็นแกนเรื่อง

- **Problem:** ระบุสถานการณ์และความเสียหาย ไม่ใช้ข้อความกว้าง เช่น “Scam เป็นปัญหาใหญ่”
- **Gap:** อธิบายว่าของเดิมทำอะไรได้แล้ว และยังพลาดตรงไหน
- **Mechanism:** แสดงเหตุและผลของระบบเป็น 3–4 ขั้น ไม่ใช้รายชื่อ Feature ที่ไม่เชื่อมกัน
- **Impact:** แยกคุณค่าต่อผู้ใช้ ธนาคาร และผลที่ต้องพิสูจน์

### 2.3 Narrow hero scenario ชนะ Feature จำนวนมาก

หนึ่งหน้าควรมี Hero Scenario เดียวที่จำง่าย เช่น:

> Fake Recruiter ขอให้ First Jobber โอนค่าสมัคร ค่าอบรม ค่าอุปกรณ์ หรือเงินมัดจำ ไปยังบัญชีบุคคลใหม่ โดยดึงจากเงินสำรองตั้งหลัก

Feature อื่นควรสนับสนุน Scenario นี้ ไม่ใช่เพิ่ม Scope ใหม่

### 2.4 บอก Novelty แบบเปรียบเทียบ

ไม่ควรเขียนเพียงว่า “ใช้ Multi-signal” แต่ต้องตอบว่าแตกต่างจากของเดิมอย่างไร:

> K-ePocket ช่วยแยกและตั้งเป้าหมายเงิน ส่วน JobShield เพิ่ม Security Policy ที่เข้าใจว่าเงินก้อนนี้คือ Protected Reserve และปรับการแทรกแซงตามความเสี่ยง ณ จังหวะก่อนเงินออก

### 2.5 Feasibility ต้องมาพร้อม Boundary

Proposal ที่น่าเชื่อถือไม่จำเป็นต้องอ้างว่าสร้างได้ครบ แต่ต้องแยกให้ชัดว่า:

- ใช้ความสามารถเดิมอะไร
- เสนอ Integration ใหม่อะไร
- Prototype จำลองอะไร
- ต้องขอ Product, Risk, Legal หรือ Business Approval ตรงไหน

### 2.6 ใช้ตัวเลขเป็น Evidence ไม่ใช่เครื่องประดับ

- ทุกตัวเลขต้องมีแหล่งที่มาและตรงกับกลุ่มประชากร
- ถ้าสถิติเป็นของคนไทยโดยรวม ต้องไม่เขียนว่าเป็นสถิติเฉพาะ First Jobbers
- ห้ามสร้าง Accuracy, Loss reduction, Adoption หรือ ROI ก่อนมีข้อมูล
- Product rate, K Point และ Benefit ที่ยังไม่อนุมัติต้องเรียกว่า Hypothesis

### 2.7 บอกวิธีพิสูจน์แทนการรับประกันผล

สำหรับ JobShield ควรใช้ Metrics เช่น:

- ผู้ใช้เข้าใจเหตุผลเตือนหรือไม่
- Pause/Cancel rate ใน Scam scenario
- Legitimate transaction completion และเวลาที่เพิ่มขึ้น
- False-positive rate
- Rule/test coverage
- เมื่อมีข้อมูลจริงจึงวัด Precision, Recall และ amount-weighted recall

### 2.8 เขียนให้ Mixed Audience อ่านได้

- Plain Thai ก่อน ตามด้วย Technical term ที่จำเป็น
- Technical term ทุกคำต้องมีหน้าที่ใน Flow
- แสดง Architecture เท่าที่ช่วยพิสูจน์ Feasibility
- หลีกเลี่ยงศัพท์ที่ทำให้ดูเกินจริง เช่น AI หากเป็น Rule-based prototype

## 3. Content hierarchy สำหรับ one-page KBTG proposal

1. **Title + one-sentence value proposition** — บอกผู้ใช้ ปัญหา กลไก และจังหวะที่สร้างคุณค่า
2. **Problem Statement + evidence** — ปัญหาเฉพาะและช่องว่างของ Authentication/คำเตือนทั่วไป
3. **Target Users** — First Jobbers อายุ 22–30 และบริบทช่วงเปลี่ยนผ่าน
4. **Proposed Solution** — Build → Detect → Intervene
5. **Novelty** — ความต่างระหว่าง K-ePocket กับ JobShield
6. **Value Proposition** — ผู้ใช้และ K PLUS พร้อมใช้คำว่า “คาดหวัง/ต้องพิสูจน์” เมื่อยังไม่มีผลจริง
7. **Track Perspective** — Defense in depth, privacy, risk-based policy, incident response และ MVP boundary
8. **Source footer** — แหล่งหลักจำนวนน้อยที่ตรวจสอบได้

## 4. สิ่งที่นำมาใช้กับ Proposal-v3

- เก็บ required English headings ครบทั้งห้าหัวข้อ
- ภาษาไทยเป็นหลักตามการตัดสินใจของทีม
- ใช้ Hero Scenario: fake recruiter ขอให้จ่ายเพื่อแลกกับงาน
- ใช้ `เงินสำรองตั้งหลัก (Protected Reserve)` เป็นชื่อเดียว
- อธิบาย Solution เป็น 3 ขั้น: Build, Detect, Intervene
- ใส่ความต่างจาก K-ePocket เป็นประโยคเดียวที่เห็นชัด
- ไม่ใส่อัตราดอกเบี้ยหรือจำนวน K Point ใน Proposal
- ไม่อ้าง AI/ML, Model accuracy, Fraud reduction หรือ ROI
- ระบุ Rule-based + synthetic data และ Metrics ที่จะทดสอบ
